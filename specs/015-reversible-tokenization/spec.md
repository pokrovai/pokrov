# Спецификация фичи: Reversible Tokenization (обратимая псевдонимизация с восстановлением ответа)

**Ветка фичи**: `feature/reversible-tokenization`
**Дата создания**: 2026-09-27
**Статус**: Draft
**Вход**: Описание пользователя: "нужно проработать режим замены с обратным восстановлением, когда ответ доходит клиенту, это нужно для скрытия контекста от ЛЛМ но так, чтобы не ломался код. например в имени пакета есть имя организации которое нужно скрывать, но если просто заменять, тогда код сломается если не восстанавливать когда ответ от ллм идет клиенту"

## Clarifications

### Session 2026-09-27

- Q: Как обратимость включается в политике? → A: Sentinel-шаблон `replacement: "[PKV_TOKEN]"` на правилах с `action: replace` (прецедент `[ID_HASH]`); `PolicyAction` enum не расширяется.
- Q: Деривация токена? → A: Детерминированный keyed-hash токен (стабилен между запросами и контурами LLM/MCP), ключ через env `SecretRef`; stateless — карта перестраивается на каждый запрос из хитов, persistent vault отсутствует.
- Q: Область восстановления? → A: LLM-прокси (JSON + оба SSE-пути) и MCP в обоих направлениях (аргументы → upstream-сервер, выход → агент).
- Q: Восстановление на raw SSE passthrough (`output_sanitization=false`)? → A: Да, на всех ответных путях; passthrough-поток оборачивается инкрементальным ре-hydrate с хвостовым буфером.
- Q: Жизненный цикл карты токен→оригинал? → A: Per-request; карта умирает с ответом, ничего не хранится между запросами. Стабильность кеша достигается детерминизмом токена, а не хранилищем.
- Q: Санитизация аргументов MCP — новое поведение? → A: Да, гейтится конфиг-флагом `sanitize_arguments` (default `false`); при включении на args применяется полная политика профиля.
- Q: MCP output restore по какой карте? → A: Только по карте аргументов вызова (восстанавливаются лишь значения, которые клиент сам отправил); новые секреты выхода обрабатываются output-политикой деструктивно.
- Q: Формат токена? → A: `__PKV_<hex32>__` — валидный идентификатор; 128-битное тело делает коллизии криптографически недостижимыми; для полноты при коллизии тела — детерминированный суффикс `_c<hex>`.

## Пользовательские сценарии и тестирование *(обязательно)*

### Пользовательская история 1 - Обратимая токенизация в LLM JSON-ответе (Приоритет: P1)

Как оператор безопасности, я хочу, чтобы чувствительные значения (имя организации, внутренние хосты, доменные маркеры) в промпте заменялись стабильными псевдонимами перед отправкой в LLM, а ответ модели возвращался клиенту с восстановленными оригиналами, чтобы код и идентификаторы в ответе оставались рабочими.

**Почему этот приоритет**: Это основная ценность фичи — скрыть контекст от LLM, не ломая клиентский код. Без неё остальные истории бесполезны.

**Независимая проверка**: Отправить chat-completion запрос со строкой, покрытой marker-правилом (например, имя организации в имени пакета), на мок-upstream, возвращающий ответ с псевдонимом; убедиться, что upstream увидел токен, а клиент получил оригинал.

**Сценарии приемки**:

1. **Given** профиль с правилом `action: replace, replacement: "[PKV_TOKEN]"` на значение `acme-corp`, **When** клиент отправляет prompt `use acme-corp-utils::init`, **Then** upstream получает текст с токеном вместо `acme-corp`, а ответ upstream, содержащий токен, возвращается клиенту с `acme-corp` на месте токена.
2. **Given** два идентичных запроса с одним и тем же чувствительным значением, **When** оба санитизируются, **Then** sanitized-представление байт-в-байт идентично (токен детерминирован → upstream prompt-cache не разрушается).
3. **Given** ответ upstream, не содержащий ни одного токена, **When** выполняется восстановление, **Then** тело ответа передаётся клиенту без изменений.

---

### Пользовательская история 2 - Восстановление в SSE-потоках (Приоритет: P2)

Как оператор, я хочу, чтобы восстановление работало и на потоковых ответах — как на пути с буферизованной выходной санитизацией, так и на прямом passthrough-стриме, — чтобы стриминговые клиенты получали валидный код.

**Почему этот приоритет**: Стриминг — основной режим реального использования LLM; без него фича покрывает только половину трафика.

**Независимая проверка**: Прогнать SSE-ответ, в котором токен разрезан границей сетевого чанка, через passthrough-путь; убедиться, что клиент получает восстановленный текст и невыпущенный хвост буфера флашится в конце потока.

**Сценарии приемки**:

1. **Given** streaming-запрос с `output_sanitization=false` и токен, разделённый на два байтовых чанка, **When** поток проходит через прокси, **Then** клиент получает события с восстановленным оригиналом и ни один байт не теряется.
2. **Given** streaming-запрос с `output_sanitization=true`, **When** поток буферизуется, санитизируется и восстанавливается, **Then** восстановление применяется к финальному телу после выходной политики.
3. **Given** незавершённый поток или обрыв соединения, **When** хвост буфера содержит неполный префикс токена, **Then** хвост флашится клиенту как есть, без подвисания.

---

### Пользовательская история 3 - Токенизация аргументов и восстановление выхода MCP (Приоритет: P3)

Как оператор, я хочу опционально скрывать чувствительные значения в аргументах tool-вызовов от upstream MCP-сервера и восстанавливать их в выходе инструмента, чтобы данные не покидали доверенный периметр, а агент получал согласованный результат.

**Почему этот приоритет**: Расширяет фичу на MCP-контур; ценно, но независимо отключаемо и не блокирует LLM-путь.

**Независимая проверка**: Включить `sanitize_arguments` на tool-политике, вызвать инструмент с чувствительным аргументом; убедиться, что upstream-сервер получил токен, а выход, содержащий токен, вернулся агенту с оригиналом.

**Сценарии приемки**:

1. **Given** tool-политика с `sanitize_arguments: true` и marker-правилом, **When** аргументы содержат чувствительное значение, **Then** upstream-сервер получает токен, а выход инструмента, эхом содержащий токен, возвращается агенту с оригиналом.
2. **Given** выход инструмента, содержащий чувствительное значение, которого не было в аргументах, **When** применяется output-политика, **Then** значение обрабатывается деструктивными действиями (mask/redact/block) без восстановления — клиент не получает данные, которых он не отправлял.
3. **Given** значение, токенизированное в MCP-вызове, затем повторно встречающееся в последующем LLM-запросе, **When** LLM-прокси санитизирует запрос, **Then** токен совпадает с MCP-токеном (общая keyed-деривация), и восстановление LLM-ответа работает согласованно.

---

### Edge Cases

- LLM мутирует токен в ответе (смена регистра, разрыв пробелом, обрезка) → exact match не срабатывает, токен остаётся видимым клиенту маркером; счётчик невосстановленных токенов фиксируется в аудит.
- Output-политика сама изменила или удалила область с токеном → токен не восстанавливается (fail-visible); событие отражается счётчиком.
- Два разных чувствительных значения дают одинаковое тело токена внутри одного запроса → детерминированный суффикс `_c<hex>` устраняет коллизию, восстановление однозначно.
- Marker-правило настроено, но ключ деривации не задан → ошибка валидации конфигурации при старте (fail-closed, без молчаливой деградации в plaintext-замену).
- Режим `dry_run` → трансформации не применяются, карта пустая, восстановление отсутствует.
- Ответ upstream содержит строку, совпадающую с форматом токена, но порождённую моделью случайно → вероятность пренебрежима за счёт keyed-пространства имён; совпадение восстановится ложно только при совпадении полного токена.
- `tools`-payload по существующему контракту `restore_tool_definitions` обходит санитизацию — токены в схемах инструментов не появляются.

## Требования *(обязательно)*

### Функциональные требования

- **FR-001**: Система MUST поддерживать opt-in обратимой замены через sentinel-шаблон на правилах с действием `replace`: сработавший фрагмент заменяется токеном, а пара токен→оригинал записывается в карту запроса.
- **FR-002**: Токен MUST быть детерминированным, производным от значения фрагмента и операторского ключа; одинаковое значение MUST давать одинаковый токен в разных запросах и на контурах LLM/MCP.
- **FR-003**: Токен MUST быть безопасным идентификатором (буквы/цифры/подчёркивания), чтобы встраивание в имена пакетов, идентификаторы и пути не ломало синтаксис кода.
- **FR-004**: При коллизии токен-префикса разных значений внутри одного запроса система MUST генерировать детерминированный различающий суффикс, сохраняющий однозначность восстановления.
- **FR-005**: Восстановление MUST выполняться на ответе LLM→клиент строго после выходной policy-оценки, на всех трёх путях: JSON-тело, буферизованный SSE, raw SSE passthrough.
- **FR-006**: На потоковом passthrough-пути восстановление MUST корректно обрабатывать токены, разрезанные границей чанка, без потери или искажения байтов.
- **FR-007**: Для MCP система MUST поддерживать опциональную санитизацию аргументов tool-вызова (config-флаг, по умолчанию выключено) и восстановление выхода инструмента только по значениям, присланным клиентом в этом вызове.
- **FR-008**: Карта восстановления MUST иметь время жизни одного запроса и MUST NOT сериализоваться, логироваться или попадать в audit/explain/trace-вывод.
- **FR-009**: Конфигурация MUST отклоняться при старте, если marker-шаблон используется без настроенного ключа деривации (fail-closed).
- **FR-010**: Аудит и метрики MUST включать метаданные-only счётчики: число токенизированных спанов и число восстановленных вхождений, без значений и без содержимого карты.
- **FR-011**: Поведение `dry_run`, `block`, `mask`, `redact` и существующих шаблонов (`[ID_HASH]`, литеральные) MUST NOT изменяться для запросов без marker-правил.

### Ключевые сущности

- **RehydrationMap**: per-request отображение токен→оригинальный фрагмент; строится во время трансформации запроса, живёт до конца ответа, не сериализуется.
- **Token**: детерминированный keyed-псевдоним фрагмента; идентификаторо-безопасная строка фиксированного формата.
- **RehydrationKey**: операторский секрет деривации токенов, разрешаемый из env при старте; отсутствие при наличии marker-правил — ошибка конфигурации.

## Ограничения безопасности и приватности *(обязательно)*

- Оригинальные фрагменты и содержимое карты MUST NOT попадать в логи, audit summary, explain, метрики или payload trace; учитываются только счётчики.
- Карта существует только в памяти обработки одного запроса; persistent-хранилище пар токен↔значение запрещено (stateless-контракт).
- Детерминизм токена раскрывает факт равенства двух значений внутри видимой LLM поверхности — принятое компромиссное свойство; токен без ключа не должен позволять восстановить значение перебором по словарю низкоэнтропийных имён.
- Ключ деривации разрешается только через env-secret ссылку, никогда не хранится открытым в конфиге и не выводится в диагностику.
- Восстановление значений, впервые появившихся в выходе (не присланных клиентом), MUST NOT выполняться — output-политика сохраняет деструктивную семантику для таких данных.

## Операционная готовность *(обязательно для runtime-изменений)*

- **Логи**: structured audit events дополняются полями `tokenized_spans_total` и `rehydrated_tokens_total`; значения и токены не логируются.
- **Метрики**: счётчики восстановленных вхождений и (для LLM) невосстановленных токенов на ответе.
- **Health/Readiness**: readiness MUST падать, если marker-правила настроены без ключа (fail-closed валидация при bootstrap).
- **Документация/конфиг**: `docs/configuration.md`, `config/pokrov.example.yaml` и `config/pokrov.test.yaml` MUST описывать sentinel-шаблон, ключ и MCP-флаг `sanitize_arguments`.

## Required Test Coverage *(обязательно)*

- **Unit**: деривация токена (детерминизм, идентификаторо-безопасность, суффикс коллизии); построение карты из хитов; восстановление в тексте и JSON-листьях; отсутствие сериализации карты.
- **Integration**: happy path LLM JSON (token→upstream, original→client); SSE passthrough с токеном на границе чанков; буферизованный SSE; MCP args+output; fail-closed старт без ключа.
- **Performance**: восстановление на representative payload в рамках бюджета P95 ≤ 50 ms совокупного overhead.
- **Security**: логи/audit/trace не содержат оригиналов и карты; значение не восстанавливается из токена перебором без ключа; output-политика на токенизированном тексте выполняется до восстановления.

## Success Criteria *(обязательно)*

### Измеримые результаты

- **SC-001**: Клиентский код/идентификаторы в ответе идентичны исходным для 100% вхождений немутированных токенов — round-trip `sanitize → upstream → restore` возвращает клиенту текст с оригинальными значениями.
- **SC-002**: Upstream никогда не получает оригинальное значение по marker-правилам: 0 вхождений фрагмента в теле, ушедшем провайдеру (проверяется интеграционным тестом на мок-upstream).
- **SC-003**: Два идентичных запроса дают байт-идентичное sanitized-представление — upstream prompt-cache сохраняется.
- **SC-004**: Дополнительный overhead восстановления укладывается в общий бюджет P95 ≤ 50 ms на representative payload.
- **SC-005**: В audit/log/trace выводе отсутствуют оригинальные фрагменты и содержимое карты (0 raw-полей).

## Acceptance Evidence *(обязательно)*

- Интеграционный тест: request с marker-значением → мок-upstream фиксирует токен → ответ клиенту содержит оригинал (JSON и оба SSE-режима).
- Тест границы чанка: токен, разрезанный байтовой границей, восстанавливается корректно.
- MCP-тест: `sanitize_arguments: true` → сервер видит токен → выход восстановлен для args-значений и не восстановлен для output-native секретов.
- Тест fail-closed: конфиг с marker-правилом без ключа отклоняется при bootstrap.
- Evidence-артефакт: результаты `cargo test -p pokrov-core -p pokrov-proxy-llm -p pokrov-proxy-mcp` и поиск по логам на отсутствие raw-значений.

## Assumptions

- Клиент (агент) — доверенная сторона; угроза направлена на upstream LLM-провайдеров и (опционально) MCP-серверы.
- Marker-правила применяются оператором осознанно: токенизированный аргумент доходит до MCP-инструмента как псевдоним; если инструмент функционально зависит от значения, это осознанный выбор конфигурации (`sanitize_arguments` по умолчанию выключен).
- Токен, сгенерированный моделью случайно, считается пренебрежимо редким; fuzzy-восстановление мутированных токенов — вне scope v1.
- Кросс-запросная и кросс-пользовательская изоляция обеспечивается отсутствием хранилища: восстановление возможно только для значений, присутствовавших в том же запросе.
- NER-сущности получают marker-шаблон только после отдельного решения по их `replacement_template` (сейчас `Some("")` — стирание); в v1 обратимость покрывает custom/deterministic-правила.
